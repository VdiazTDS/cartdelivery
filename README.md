# Cart Delivery (TDS-PAK)

A static frontend with a Supabase backend for planning and recording cart (trash/recycling) deliveries on a map. Route stops come from Excel/CSV files stored in Supabase; drivers select stops on the map and mark them delivered. It is used mainly on an **iPhone 16 Pro Max**, so phone usability comes first.

## Run it
No frontend build step. Serve the folder statically over HTTPS (or localhost for development). Needs internet for CDN libraries, map tiles and Supabase. **Delivery profiles require the database migration and Edge Function in [supabase/SETUP.md](supabase/SETUP.md) before publishing this frontend.** The new app blocks direct edits of shared originals.

Check code: `node --check app.js` and `git diff --check`. AI assistants: also read [AGENTS.md](./AGENTS.md).

## Data model
Route files are Excel/CSV; only the **first sheet** is read. One row = one stop.

| Column | Use |
|---|---|
| `LATITUDE`, `LONGITUDE` | Marker position (rows without them are skipped) |
| `ROUTE`, `DAY` | Route id and weekday number 1-7 (Monday=1); grouping, filters, colors. `NEWROUTE`/`NEWDAY` are ignored |
| `CSADR#`, `CSSDIR`, `CSSTRT`, `CSSFUX` | Address parts (number, direction, street, suffix) |
| `SIZE`, `BINNO` | Container details in the stop popup; `BINNO` also appears on its own labeled line in each Choose a stop entry |
| `QTY` | Cart quantity in the popup; finite numeric values greater than 1 also get a map badge and a quantity hint in the nearby-stop chooser |
| `SEQNO` | Optional finite, nonnegative number or numeric text (zero allowed); shown in popup/chooser and the sequence overlay |
| `del_status` | `"Delivered"` (case-insensitive) = all carts done; empty = pending, including partial delivery |
| `del_qty` | Delivered cart count, saved with status in the route workbook. A valid whole number from 0 through QTY takes precedence; older rows without a valid count use del_status |

Existing files in `excel-files` are imported on first open. Managed originals and private profile copies are immutable Excel versions in the private `profile-workbooks` bucket, with current-version pointers in PostgreSQL. Original uploads remain available for recovery. Old public Excel URLs remain frozen initial snapshots; use **View original** in this app to open/download the current shared version. Files named like "route summary" are ignored.

## Key runtime state (`app.js`)
- `window._currentRows / _currentWorkbook / _currentFilePath`: the loaded file; used when saving. `profileState.workspace` supplies the immutable dataset ID, profile-copy revision, signed-in owner, view/copy mode, and pending record count. Never infer ownership from a filename or accept a client-provided owner on the server.
- `routeDayGroups["ROUTE|DAY"]` and `["ROUTE|Delivered"]` = `{ layers: [markers] }`; drives filter checkboxes (`buildRouteDayLayerControls`) and visibility (`applyFilters`).
- Each marker: `marker._rowRef` (its row object), `marker._base` (`{lat, lon, symbol}`).
- Multiple carts: `multiCartQuantity(row)` accepts numeric `QTY` or numeric text greater than 1. `attachQuantityBadge(marker, row)` attaches a noninteractive `marker._quantityBadge` in `quantityPane` above the Canvas stops. Its add/remove events follow the stop's visibility; it is not part of selection or marker counts. `quantityBadgesToggle` hides/shows the pane without changing stop layers.
- Stop search: markers lazily cache `_addressSearch` address tokens and normalized bin identifiers. `addressSearchTokens()` normalizes text/abbreviations; `addressSearchScore()` ranks address matches, while `binSearchText()` matches bin identifiers separately. `initApp()` owns search filters, totals, the result list, and a separate noninteractive preview ring. `resetAddressSearch()` clears them on file load/reset; `refreshAddressSearch()` rebuilds scope options and updates results after map filters and confirmed delivery changes.
- Selection: `drawnLayer` (polygon/rectangle), `individuallySelectedMarkers`, `individuallyDeselectedMarkers`. **A stop is selected iff its marker is visible** and either it is in the first set or it is inside the drawn shape and not in the second. Always use `isStopSelected(marker, tester)` (`createSelectionTester()` builds the polygon test once).
- `sequenceGroups`: a `Map` keyed by `JSON.stringify([route, day])`, separate from marker groups. Each group contains `{ route, day, stops }`; each stop holds `{ row, seq, index, latlng }`, with `latlng: null` for an invalid location. Row references are shared with `_currentRows`, so confirmed delivery changes update styling without changing sequence order.
- `mobileStopSelectionMode`: phone tap-selection mode flag.
- `localStorage`: `cartdelivery.savedFiles.cartDelivery` (local cache of the Cart Delivery tab list; the real, shared list is the hidden bucket file `_cart-delivery-tab.json`, see `SHARED_TAB_FILE`), `sunMode` (`on`/`off`), `cartdelivery.quantityBadges` (`on`/`off`, defaults to on).

## Main flows
1. **Sign in and open file**: create a unique username/password, then use the saved-files modal (`listProfileFiles`). **Create my copy & open** makes a separate workbook associated with that profile; subsequent opens resume it. **View original** is read-only. Upload adds a new original and creates the uploader's copy; it never replaces an existing original. `processExcelBuffer(buffer)` clears old map state and builds markers. The modal opens on the shared **Cart Delivery** tab; **All Files** includes managed and legacy originals.
2. **Select**: desktop clicks markers or draws polygons; phone uses **Select Stops** mode. `handleMobileStopTap` selects the nearest stop, or shows the chooser when the two nearest are within 12px. Finish with **Done**. With Select Stops off, a phone tap only opens the customer details popup (no selection).

   **Choose a stop** lists each record's `BINNO` on a separate **Bin #:** line beneath the address, making overlapping addresses easier to distinguish. Numeric zero is displayed, text identifiers retain leading zeros, and blank/missing values say **Not provided**. Bin values are displayed as text and long values wrap within the entry.
3. **Deliver carts / undo**: `persistDeliveryChanges()` sends only changed editable fields to `saveProfileWorkbook()`. The server generates an immutable Excel copy and commits it only if the expected profile revision still matches. Only after confirmation and fetching that saved workbook does the client update rows, markers, and counts. With QTY 2+ off it adds one cart per selected pending stop; with it on it opens a per-record quantity prompt. **Data trust rule: markers/rows change only after a confirmed save; never make this optimistic.** Originals change only through the profile panel's explicit **Review & sync** flow. Sync compares baseline/my copy/current original, requires decisions for overlapping records, and commits both the new original and audit history in one database transaction. The header's username button shows pending changed records.
4. **Layout**: `placeDeliveryControls()` moves the same buttons between the phone dock (below the map) and the desktop sidebar at 900px. `syncMobile*Layout` publishes `--mobile-controls-height` / `--mobile-header-height` CSS variables through a `ResizeObserver`.
5. **Location**: Locate (follow GPS + heading); Copy Location (nearby addresses + coordinates for truck handoffs).
6. **Sequence arrows**: open **Menu → Delivery sequence** on phones (**Delivery sequence** in the left sidebar on desktop). Choose **Original file** or **Saved Optimo**, then choose a **Route to display**. Either choice shows the arrows immediately. **Show arrows on map** hides them without hiding the picker or changing the source used for stop numbers. Original paths include delivered stops and remain independent of marker visibility. See [Sequence overlay](#sequence-overlay) for styling and data rules.
7. **Truck / trailer loads**: open **More → Truck / Trailer Loads** on phones (right sidebar on desktop). Choose or create a shared truck count profile, such as **Burnet**. Manually record a load only after the crew finishes unloading it: truck/trailer, optional vehicle name, unloading date/time, approximate trash and recycling quantities. Each trip counts once. Profiles are independent of route files and cart delivery order. All-date or today totals exclude voided entries; today uses the viewing phone's local date. A mistaken load can be voided and replaced; its history remains visible.

### Pocket lock

Tap the **lock icon** at the top right of the header, beside the Light/Dark Mode toggle, before putting the phone in your pocket. The button is in the same place on desktop. A transparent full-screen modal keeps the map and controls visible while blocking taps, without changing selected stops or delivery data. A compact unlock panel sits above the phone dock (at the bottom on desktop); the map continues updating while locked. Hold **Hold to unlock** still for two seconds, then release; a progress bar and release prompt guide you. Keyboard users can hold Space or Enter on the button. Short taps, movement, multiple touches, Escape, losing focus, and switching apps cannot complete the hold. Returning to the page keeps it locked; reloading starts unlocked. Browser and phone system controls are outside this site lock, and normal screen auto-lock still applies.

`setupPocketLock()` uses a native modal dialog to keep underlying controls inert. The unlock happens after release to prevent taps passing through. Check with `node tests/pocket-lock.browser.cjs` (same Playwright dependency as the resequencing test).

### Basemaps, city limits and address numbers

**Map View** offers OpenStreetMap streets, Esri satellite imagery, Esri Imagery Clarity, Esri minimal light/dark gray streets, and Austin local aerials. The minimal views use Esri rather than CARTO so no CARTO API key is required. Clarity can show older imagery. Austin aerials have regional coverage, with an inline notice outside their footprint. The city's cached tiles and gray maps use native zoom 16 and scale at closer zooms; normal satellite/Clarity use native zoom 19. Closer zooms do not imply newer or higher-resolution imagery.

`setBaseMap()` is the single basemap switch handler. It removes the previous layer before adding the selected one; inactive basemaps are not prefetched. All tile layers load after movement settles, skip intermediate zoom loading, and keep a one-tile buffer. A single transportation-label layer accompanies aerial views at zoom 15 or closer. Provider credits use compact 1px text at the upper right on phones and lower left on desktop, clear of the delivery controls and desktop action panel. They do not intercept pointer taps; provider links remain keyboard-accessible. The optional Leaflet branding prefix is omitted. `placeMapCredits()` updates their corner when crossing the 900px layout breakpoint. Map view changes do not change stop selection, filters, colors, sequence, or delivery data.

Expand **Map overlays** and enable **City limits** to show translucent pink city areas with a bold magenta border, a white outline for contrast, and city names over any Map View. It defaults off each session, covers U.S. incorporated places (including Texas), and does not show unincorporated census-designated places or ETJs. The [Census TIGERweb service](https://tigerweb.geo.census.gov/arcgis/rest/services/TIGERweb/tigerWMS_Current/MapServer/28) supplies reference boundaries, which can lag recent annexations. Names appear where the service's scale/label placement allows them. Shading remains visible inside a city even when its boundary is outside the viewport.

`cityLimitsLayer` groups two noninteractive Canvas GeoJSON layers (7px white edge, 3.5px magenta border, 14% pink fill) and WMS city-name tiles (layer 48). The incorporated-place polygons come from Census REST layer 28, using a viewport envelope with a 15% margin, zoom-dependent simplification with a roughly 5m floor, six decimal places, and at most 80 features. Polygon holes and multipart boundaries are preserved. Busy views report the cap and ask the user to zoom in. Requests wait for a 350ms pause, time out after 12 seconds, and abort on movement, zooming out, or disabling the layer; stale results cannot reappear. Up to four viewport/zoom responses are cached in memory for five minutes and cleared when disabled. Errors clear polygon results and show an off/on retry message. Disabled/below-zoom-9 layers make no requests.

The polygon pane (280) and name pane (281) sit below address numbers, sequence arrows, and stop markers. All map gestures pass through; stops, selections, filters, and delivery saves remain independent. Name tiles retain transparent 512px images, no offscreen buffer, and no world wrapping. Census GetMap images share the bounded 600-tile service-worker cache; live boundary queries bypass service-worker caching. Service-worker caches are v5. No extra libraries are required. Query parameters follow the [ArcGIS query documentation](https://developers.arcgis.com/rest/services-reference/enterprise/query-map-service-layer/); the public Census GeoJSON response and browser access were verified around Burnet on October 9, 2026.

Expand **Map overlays** and enable **Address numbers** for Austin-area city address points. It defaults off each session, works with any basemap, and displays house numbers rather than customer/bin data. It is separate from the loaded route file, is not selectable, and hides while selecting stops on phones or drawing/editing shapes. Outside the Austin area, below zoom 18, or while disabled/paused, it makes no address requests. Empty views and service failures appear inline.

`CityAddressNumbers` renders one noninteractive canvas in `addressNumberPane` below stop markers. After a 400ms pause, it queries the current viewport plus a small margin from the [Austin address service](https://maps.austintexas.gov/gis/rest/Shared/Property/MapServer/0), requests only address-number fields and coordinates, and caps responses at 400 features. Grid collision checks limit drawing to 120 labels on phones / 220 on desktop, with device pixel ratio capped at 2. No per-address markers/tooltips or citywide downloads are created. Panning/zooming cancels pending work and hides old labels; stale responses cannot replace the current view. Requests time out after eight seconds. Up to six viewport results are cached in memory for two minutes and discarded when disabled. Status/quantity saves never change this reference data.

Sources: [Esri Imagery Clarity](https://www.esri.com/about/newsroom/arcwatch/learn-how-to-use-world-imagery-clarity-as-your-basemap), [Esri light gray map](https://doc.arcgis.com/en/data-appliance/7.2/maps/world-light-gray-base.htm), [Austin aerial service](https://maps.austintexas.gov/gis/Image/MapTiled/AerialImagery_WebMercator/MapServer). The aerial service's description and layer-year labels differ; the app intentionally does not claim an acquisition year. Coverage, tile detail, and address completeness vary by location.

The sidebar has two side-by-side dropdown buttons: **Delivery sequence** and **Cart quantities**. Cart quantities contains Show quantity badges and Only show QTY 2+ on map. Each opens its own full-width settings below the buttons and closes the other; tapping the open button collapses it. Opening or closing a dropdown does not change the map settings.

### Sequence overlay

Blue lines and arrowheads connect consecutive stop coordinates in numeric `SEQNO` order within each original `ROUTE`/`DAY`. These are straight connections, not road directions. Stops on different routes or days never connect. Duplicate sequence values retain spreadsheet row order.

| Display | Meaning |
|---|---|
| Blue connection | At least one endpoint is pending |
| Gray dashed connection and gray arrows | Both endpoints are delivered |
| Green check badge | Delivered stop, including when its regular marker is hidden |

Rows with invalid `SEQNO`, a blank route, or a day outside integer 1–7 are omitted from the overlay with a notice. Rows with valid grouping/sequence but invalid coordinates stay in the ordered list and break the path; the overlay never bridges that missing location. Consecutive stops at the same coordinate have no connection. The toggle is disabled unless the selected source and route/day have adjacent stops with distinct valid locations. These rules apply to the overlay; `rowSequence()` can still show a valid sequence in a marker popup or nearby-stop chooser.

`syncSequenceControls()` keeps the two source buttons, route options with stop counts, and toggle availability in sync. Only routes with stops in the chosen source appear; switching sources retains the chosen route when available, otherwise selects all. Empty Optimo results show an explanation and no original-sequence fallback. The card's On map/Off indicator and status reflect the active display; **About the arrows** contains the optional legend. Source selection uses the existing hidden `sequenceSource` control as its shared value.

**Show sequence numbers** is on by default and works independently of arrows. Small `#12` badges beside visible stop markers use the selected source and route/day: original `SEQNO` (including zero) or saved Optimo stop numbers. Unscheduled Optimo records are never numbered. Numbers follow marker filters and refresh after confirmed delivery changes; delivered records use green badges. A single noninteractive `SequenceNumberLabels` canvas in `sequenceNumberPane` draws only viewport labels, with grid collision checks to keep crowded labels from overlapping. Zoom in for more labels, or tap a stop to read its exact number in the popup/nearby-stop chooser. Labels do not change workbook fields, selection, or delivery status.

`rebuildSequenceData(rows)` runs on file load and Reset Map, rebuilding groups and the route/day dropdown. Loading another file resets the dropdown to all sequences and retains the enabled toggle only if a drawable sequence exists. Reset Map clears and disables it. Original sequence controls are session state. A matching phone-only Optimo sequence is restored and enabled when its file is reopened; neither sequence changes the workbook's `SEQNO`.

`scheduleSequenceRender()` combines redraw requests into one animation frame. `renderSequenceLayer()` reads the confirmed row status and updates batched Canvas paths in `sequencePane` (z-index 350, below regular stop markers). The pane and paths are noninteractive, preserving map taps and selection. Badges and arrowheads use projected pixel offsets and redraw after pan, zoom, or resize. Arrow placement is clipped to the viewport and capped at 1,500 per view; lines remain complete, and short connections may have no arrowhead. After a confirmed save/undo, the shared row references supply the new status and only a redraw is needed.

### Generate a new sequence with OptimoRoute

Open **Menu → Delivery sequence → Plan with OptimoRoute** (Delivery sequence in the desktop sidebar). Enter the OptimoRoute API key on the phone, choose the planning date, and use **Stops to plan** to choose **Selected stops**, **Selected visible stops**, one original `ROUTE`/`DAY`, or **All route/day groups**. Selected stops includes selected records on enabled layers even if off-screen; Selected visible stops also requires them to be in the current map view. The summary counts the undelivered records to send, and only relevant driver inputs are shown with their actual counts. Delivered records are always excluded; duplicate addresses and multiple bins remain separate records. Invalid coordinates outside the chosen scope do not block planning. Each included route/day needs its own dedicated driver.

For **Selected visible stops**, first use **Select Stops** on the phone (or clicks/a drawn area on desktop), then open the planning dialog and choose that option. `selectedVisibleSequenceRows()` uses `isStopSelected()` with one shared polygon tester and checks the current map bounds. Hidden layers, off-screen stops, delivered stops, and explicit deselections inside a drawn area are excluded. Generation captures those row indices before GPS/API work; later panning or selection changes cannot add orders to an active run. An empty selection stops before date clearing or upload. Reopening the dialog with a different visible selection invalidates the old preview. Saving replaces the entire local Optimo snapshot, so unselected stops have no Optimo number or arrow, including stops in a previously saved sequence. Choosing **Original file** still explicitly restores spreadsheet numbering. Route/day and all-groups modes continue to include hidden and off-screen records in their scope.

**Clear planning date & generate** first validates the selection, date, driver IDs, and GPS (if selected), then calls `POST /delete_all_orders` with the exact planning date. This deletes **all OptimoRoute orders and planned routes on that date in the API key's account**, including other route/day groups and orders not created by this app. The screen displays the date and deletion scope before the button is pressed. Other dates are untouched. No driver update, upload, or planning request is sent until OptimoRoute confirms deletion with `success: true`. A deletion error, unconfirmed response, or lost connection stops the run; a lost response may mean deletion happened remotely. The API wrapper independently rejects missing, invalid, or mismatched dates because omitting the date would delete the entire account's orders. Clearing occurs once per new generation, never between sections or on **Check planning result**. Tests simulate all deletion requests; they never delete live account data.

**Planning size** defaults to **All selected records at once**. Uploads still use batches of up to 500, but all selected orders are included in one planning request. The upload limit and the account's planning limit are different: `ERR_OPT_REQUESTS_EXCEEDED` means too many orders for planning. Uploading in batches alone does not solve it. Published limits are 700 orders at once for Lite and 1,000 for Pro; Custom limits vary ([OptimoRoute pricing](https://optimoroute.com/pricing/)). An account with sufficient capacity is needed to plan a larger selection together.

Optional 500- or 100-record sections still plan one section at a time per route/day. Each section replaces the earlier plan on that driver/date: only the last section remains scheduled. Sections are partitioned in original sequence order and visited nearest the current start, with each later section starting at the previous section's final returned stop. **The phone no longer joins section results.** This mode cannot leave a whole large route scheduled on the website. No local fallback creates stop sequences.

After planning finishes, the app fetches each selected driver's routes again. Only selected order IDs actually present in those final server routes receive a sequence number or arrow. Numbers preserve OptimoRoute's `stopNumber`, including gaps. Missing orders are reported as unscheduled; a partial or empty result may be saved. Duplicate, unexpected, or invalid stops still reject the result. Orders from earlier sections and failed runs can remain in OptimoRoute without being scheduled. Keep the page open until planning and the final read finish.

The default start is the phone's current GPS location; GPS requires HTTPS (or localhost) and browser permission. **Choose start on map** and **Choose end on map** temporarily close the dialog and open a location picker below the map on phones. Tap the map to place a labeled Start/End pin, drag it or tap again to adjust, then press **Confirm start/end**. **Place pin at map center** also supports choosing a point without tapping the map. Panning leaves the pin at its chosen coordinates; confirmation stays disabled until a pin is placed. **Cancel**/Escape keeps the previous setting. Sequence numbers/arrows and quantity badges are temporarily hidden, and stop markers are dimmed while picking; their settings are restored afterward. The app restores the prior map center/zoom so endpoint picking does not change which selected stops qualify as visible. Stop selection taps and live GPS following are suspended during picking; existing selections remain intact. Pins are routing endpoints, not additional delivery records, and the same endpoint choices apply to each selected route/day. Chosen points last for the current open file/session and clear when another file is loaded.

Start options are GPS, a map point, or the driver's configured start. End options are a map point, the driver's configured end, or return to start. Generation validates map coordinates before clearing the planning date. Every driver update explicitly sends `startLocation` and `endLocation` using the documented `custom`, `employeeDefault`, or (end only) `startLocation` types, clearing obsolete date-specific overrides when defaults are chosen. Section mode continues its later starts from the preceding section's last returned stop. On every generation the app sets selected drivers' work window to **00:00–23:59**. Orders use zero service/check-in time, zero loads, and no time-window, skill, or vehicle-feature requirements. Mid-route depot trips are disabled.

OptimoRoute still schedules travel within driver availability and account limits; its documented API has no ignore-all-constraints mode. Configure dedicated drivers in **Administration → Drivers** with **Schedule break** and **Limit route distance** disabled and no restrictive service areas. To finish at the last delivery instead of a chosen endpoint, configure that driver end setting and choose **Driver's configured end location**. Breaks, distance limits, and the last-stop mode are not exposed as options in the documented bulk driver update API. The driver import workbook uses all-day hours, zero break duration, and blank distance/vehicle/skill fields; check existing drivers after import because blank cells may not clear existing values. A complete sequence is never claimed when OptimoRoute omits records.

Driver external IDs default to `CART-<ROUTE>-<DAY>`, for example `CART-TRASH-1` and `CART-RECYCLE-2`. Import/configure those drivers in OptimoRoute first, or enter matching existing IDs in the dialog. Each group must use a distinct dedicated driver. The app does not create drivers, dispatch routes, send notifications, or change cart delivery status. Each generation clears the selected planning date first and creates separate `CD-<run UUID>-<row index>` orders. Partially uploaded runs remain until that date is cleared by a later generation or managed in OptimoRoute.

After input and GPS validation, generation switches the map to an empty Optimo display and saves that empty state before submitting date clearing. This invalidates all old local groups, including unselected groups whose orders are cleared from the same date. Errors cannot leave old Excel or Optimo arrows looking like the new plan. After the final server read, the dialog shows scheduled/selected/unscheduled counts and previews up to three scheduled stops per group. **Use sequence on this phone** saves only this snapshot; omitted records get no sequence number or arrow. Long-running plans offer **Check planning result** to resume without clearing or uploading the same section again. Refreshing loses unfinished progress. Saved snapshots work offline but do not automatically sync later edits made on the OptimoRoute website.

The **Original file / Saved Optimo** buttons switch the sequence source. Arrows, popup sequence numbers, nearby-stop details, and address-search results use only the selected source, with no fallback to spreadsheet numbers in Optimo mode. Stops delivered after generation remain in the saved path with confirmed-delivery styling. Undoing an excluded record shows missing coverage for the displayed route/day. Map filters, selection, workbook rows, and shared cloud data are independent of the local sequence.

Implementation:

- `optimoSequenceGroups` holds the phone's route/day paths, and `optimoRowSequences` maps shared row references to new sequence numbers without adding spreadsheet fields. `rowSequence(row, true)` always reads original `SEQNO`.
- `cartdelivery.optimo.sequence.<SHA-256>` in localStorage stores version-2 snapshots: ordered row indices, matching server stop numbers, route/day/driver labels, and planning timestamps. The fingerprint includes file path and canonical row content excluding `del_status` and `del_qty`. Old version-1 joined sequences are hidden on restore and require regeneration. Clearing browser data removes snapshots; they are not shared with another phone/browser.
- The optional remembered key lives only in `cartdelivery.optimo.apiKey`. **Forget key** removes it. It is never put in source, exports, workbook cells, or Supabase. Browser storage is not encrypted and is accessible to this site's scripts. Optimo API calls go directly to `https://api.optimoroute.com` with no-store caching, omitted credentials, and no referrer. The service worker explicitly bypasses this host; its cache version changed to remove older caches.
- Uploads use batches of at most 500 with `CREATE` and unique run IDs. `optimoPlanningSections()` builds planning requests; `readOptimoPlanning()` advances or resumes them, then fetches the authoritative final routes. Planning passes explicit `useDrivers` and `useOrderObjects`, with `includeScheduledOrders: false`. Result matching uses generated order IDs and numeric stop order, never addresses or marker style. Per-order and per-driver success is checked as well as top-level responses. Planning temporarily disables delivery saves; delivery status remains upload-before-mutate.
- API contract: [OptimoRoute API reference](https://optimoroute.com/api/), checked October 8, 2026. CORS preflight for JSON POST was verified without credentials. Live account planning has not been tested; browser tests intercept all Optimo and Supabase traffic.

Regression test: install the browser test dependency with `npm install --prefix local-artifacts/test-tools playwright --no-audit --no-fund`, then run `node tests/resequence.browser.cjs`. It uses installed Chrome (override `CHROME_PATH` if needed), a temporary local HTTP server, generated workbooks, fake GPS, and intercepted APIs. Screenshots and dependencies stay in ignored `local-artifacts/`; there is still no application build step.

### Deliver carts in multiple passes

1. With **Only show QTY 2+** off, select the stops visited and tap **Deliver 1 cart per stop**. Each selected pending record receives one additional delivered cart. A QTY 1 record becomes complete; a QTY 3 record goes from 0/3 to 1/3 and stays pending. If it already has a confirmed count, one is added to that count. Use **Record carts** to explicitly specify a different quantity or total.
2. For the second pass, open **Menu > Cart quantities** and enable **Only show QTY 2+**. QTY 1 or less, blank, and invalid quantities are hidden. The filter combines with the route/day and Delivered layer choices; toggling it does not change delivery counts. Search retains its separate Multiple carts filter. Sequence connections with an excluded endpoint are omitted rather than joined across the hidden stop.
3. With that filter on, the main button becomes **Enter carts delivered**. It opens a separate blank quantity field for every selected pending record, identified by address, bin, route, and day. Enter how many carts were delivered **this visit**; the preview shows the resulting total and remaining quantity. Enter 0 to skip a record. No upload starts until valid quantities are entered and **Save cart counts** is pressed. Close/Escape cancels without changing any count.

Badges show **delivered/required**. A stop stays pending until all its carts are confirmed. Record carts defaults to the same per-record prompt while QTY 2+ is on. Its operation selector also supports explicitly adding the same quantity to every stop or setting the total delivered so far. Each record has its own field, including selections larger than the bulk preview's 50-row limit.

To correct a count, select the stop, choose **Set total delivered so far**, and enter the correct total, including 0. To correct an older Delivered stop after only a first pass, enable its Delivered layer and set its count to 1; it returns to the pending group if more carts remain. **Undo Delivered** restores a completed stop to 0. Existing Delivered rows without valid del_qty are treated as fully delivered; the app never assumes their old status meant a first pass.

Counts belong to each spreadsheet record/bin, even when records share an address. Record carts requires a positive whole-number QTY for every selected stop and rejects fractional/negative counts and counts above any stop's QTY. The preview applies to the captured selection; hidden stops are excluded by `isStopSelected()`. Invalid selections save nothing. An all-zero per-record visit also saves nothing, and zero entries leave their records unchanged. The unfiltered delivery action retains status-only completion for rows without a usable QTY; known multiple-cart quantities must be whole numbers to use it. New quantities are stored in `del_qty` in that profile's workbook, available when the same profile reopens it on another phone, and included in downloads. Other profiles see these changes only after explicit sync to the original and refreshing their copies. Rows, badges, status groups, search totals, and workbook state change only after upload success. Failed saves retain the previous state for retry. Different profiles can edit concurrently. Two phones editing the same profile copy use version checks; a stale save is rejected and the phone must reopen the copy.

`cartTotal()`, `storedCartCount()`, `deliveredCartCount()`, and `isDeliveredRow()` centralize quantity/status reads. `persistDeliveryChanges()` handles both partial counts and the main delivery/undo controls, preserves other sheets, and guards against a different file opening during upload. Count changes do not invalidate a saved Optimo sequence fingerprint. The QTY map filter is session state, starts off on page load, and does not write to the workbook. `applyFilters()` combines route/day, layer choices, and the quantity filter, including after saves.

Run `node tests/cart-counts.browser.cjs` with the existing Playwright test dependency. It uses generated workbooks and fake uploads to check delayed/failed saves, first and second passes, legacy correction, one-cart default deliveries, per-record prompts, undo, persisted counts, invalid quantities, filter combinations, file switches, and phone/desktop layouts in both themes.

### Multiple-cart indicators

Stops with a positive whole-number `QTY > 1` show an amber delivered/required badge, such as **0/2** or **1/3**, in both themes. Fully delivered badges are green when that layer is visible. Fractional quantities greater than one keep a total-only badge and cannot be edited with Record carts. Numeric text such as `"2"` also works. Blank, invalid, nonfinite, or quantities of 1 or less have no badge. Popup details, nearby-stop choices, and search results show delivered and remaining counts.

Expand **Cart quantities** in **Menu** on phones or the left sidebar on desktop, then turn **Show quantity badges** on/off. Its dropdown sits beside **Delivery sequence**; city limits and address numbers stay in the separate **Map overlays** section. The delivery dropdowns start closed and show one panel at a time. Closing a panel keeps its overlays active. Quantity badges default to on and remember the choice in this browser across reloads and file changes. The toggle controls only the badges; quantities remain available in stop details and the nearby-stop chooser.

When enabled, badges stay visible during selection, preserve route and delivery marker colors, and appear only when their stop marker is visible. Hidden delivered markers have no quantity badge; showing the delivered layer brings it back. Badges follow confirmed delivery/undo visibility changes, and file changes or Reset Map remove the old badges. They do not intercept map gestures or add selectable records.

### Address search

Search the loaded file by house number, street, or a combination (for example, `1234`, `Oak`, or `1234 N Oak St`). Results update after a short typing pause; Search or Enter runs immediately. Search ignores case, extra spaces, accents, and punctuation, and recognizes common direction/street abbreviations (`N`/`North`, `St`/`Street`, `Rd`/`Road`, etc.). Query words can appear in any order. Partial street names match; house numbers match exactly or from the start, so `123` can find `1234` but not `9123`. Exact house numbers rank first, with full address matches highest and natural address ordering for ties.

`BINNO` is searchable in the same box (optionally prefixed with `Bin`). Bin matching ignores case, spaces, and separators, supports exact or starting-prefix matches, and does not apply address abbreviations. Exact bin matches rank above address matches. Leading zeros are preserved when the spreadsheet stores the identifier as text.

**All**, **Pending**, and **Delivered** choose delivery status; **Multiple carts** is an independent `QTY > 1` toggle that can combine with either status. All resets status and the multiple-cart toggle, retaining the route/day scope. Expand **Route / day** to choose original routes and days from the loaded stops, including delivered stops' original days. These controls narrow only search results and leave map filters and selection unchanged. Filters work without a typed query; Search or All with an empty box browses all stops in the selected scope.

The cart summary counts every matching stop, including matches beyond the displayed page and hidden layers. **Carts remaining** sums pending stops' finite, nonnegative numeric `QTY` values minus their confirmed delivered counts (numeric text and zero are accepted). Blank, invalid, negative, or nonfinite quantities are not assumed to mean one cart: the summary labels the known cart subtotal and reports how many pending stops are missing QTY. Delivered stops contribute to the stop count but not remaining carts. Confirmed saves/undo refresh filters, result status, and totals; failed or unfinished saves leave them unchanged.

Results include all stop markers in the current file, including hidden and delivered layers. Each result shows its address, original route/day, sequence/bin when present, quantity, delivery status, and a **Hidden layer** hint where applicable. The list starts with 50 results and offers **Show more** in batches of 50. No-match and missing-file messages appear inline.

Clicking a result centers the map, closes Menu on phones, and shows a blue preview ring and details. This separate preview leaves marker filters, route/delivery colors, and delivery selection unchanged; hidden stops remain hidden in their regular layers. Stop-selection mode retains its existing popup suppression on phones. Changing the query or search filters removes the preview. Emptying the query keeps active filters; otherwise it hides results. Clear, Escape, loading another file, or Reset Map clears the query, search filters, totals, and preview. Search state is not saved to the workbook or localStorage.

### Shared load storage
- **Download Excel · selected profile** exports the selected profile and date filter, including all matching history beyond the first 30 displayed entries. The workbook has **Summary** totals and **Load History** sheets, with numeric cart quantities, UTC/local dates, IDs, and voided entries clearly marked and excluded from totals. It exports the currently loaded confirmed snapshot; refresh first for the latest data. The summary includes export and last-refresh timestamps. Downloads do not change cloud data.
- Profiles, loads and voids are small, immutable JSON objects in `excel-files/_cart-loads/`, hidden from Saved Files. No Excel upload or database migration is required for this log. It uses the bucket's existing list/read/insert permissions.
- Profile filenames use a SHA-256 hash of the normalized name, so creating **Burnet** on another phone opens the same profile. Each load has its own UUID; a void uses the original load's UUID in a separate file. Writes use `upsert: false`, and retries check the existing record before reporting success. Independent load additions do not overwrite one another.
- Counts change only after a confirmed write. Opening the panel, returning to the app or reconnecting refreshes the shared log; it also polls every 30 seconds while visible. Listing is paginated, and immutable entries already read in this session are reused. Failed refreshes keep the last complete snapshot and show a warning, rather than displaying partial totals.
- Only the last selected profile ID is stored in localStorage (`cartdelivery.loadProfile`); profiles and counts live in cloud storage. New phones do not need the old phone's local data. Load logging requires a connection; it is not an offline queue.
- Test with a fake bucket shared by two browser sessions: create profiles and simultaneous loads, retry a lost upload response, reject saves/reads, void entries, and switch route files. Never test writes against the real bucket.

## How-to recipes
- **New shared button**: add it in `index.html`, place it in both branches of `placeDeliveryControls()`, style both layouts.
- **Delivery control appearance**: shared buttons use `delivery-action` and `data-action` for purpose colors and decorative CSS icons. The final action styles in `style.css` cover both themes, active/disabled/saving states, and the phone/desktop placements. Keep text labels; JS updates them without removing the icons.
- **Different route/day column names**: change only `rowRoute()` / `rowDay()` in `app.js`; every other place (grouping, nearby-stop chooser, delivered save) reads route/day through them. Never read `row.ROUTE`/`row.DAY` directly.
- **Sequence column or appearance**: parse sequence values in `rowSequence()`, group/sort in `rebuildSequenceData()`, and draw in `renderSequenceLayer()`. Keep original row references and ordering independent of marker visibility. Styling lives in the sequence Canvas paths in `app.js`; sidebar controls use the final `.sequence-controls` rules in `style.css`.
- **Map overlay controls**: quantity and sequence controls share **Delivery sequence** (`#deliveryOverlaysSection`); city limits and address numbers share **Map overlays** (`#mapOverlaysSection`). These independent native `details`/`summary` disclosures start closed, open with a tap, Enter, or Space, and only hide sidebar controls, preserving overlay state. Both use `.map-overlays` and `.map-overlay-content` for shared styling. The inner `.map-overlay-card` rows use visual examples and switches backed by native checkboxes. Keep the existing input IDs, accessible descriptions, 44px targets, keyboard focus, and disabled sequence state. Scoped theme colors override the earlier sidebar-wide light-theme rules.
- **New spreadsheet column in popups**: extend `popupContent` in `processExcelBuffer` (and `showNearbyStopPicker` if relevant).
- **Tap sensitivity**: `getNearbyVisibleStops` (hit radius) and `handleMobileStopTap` (12px ambiguity threshold).
- **Stop matching**: extend `ADDRESS_SEARCH_ALIASES`, `addressSearchTokens()`, `addressSearchScore()`, or `binSearchText()`; caches contain only stable address/bin fields. Read current status and quantity directly from rows, and route/day via `rowRoute()`/`rowDay()`. Render spreadsheet text with `textContent`. Keep search navigation separate from `isStopSelected()` and real marker styling.
- **New selection-based action**: iterate `routeDayGroups`, filter with `isStopSelected`, then call `updateSelectionCount()` and `updateUndoButtonState()`.
- **Saving a file**: `saveWorkbookToCloud(rows, workbook, filePath)` delegates to the authenticated profile API. It never directly uploads a route workbook from the browser. On an uncertain response, leave rows unchanged and reopen the profile copy to establish what the server saved.
- After editing `app.js`/`style.css`, bump `?v=` in `index.html`.

## Known quirks / cautions
- `initApp()` is large; some helpers (e.g. `setMobileStopSelectionMode`) are declared inside it or inside `if` blocks. `updateSelectionCount` is re-assigned in the mobile selection section to also update the phone button.
- The Supabase key in `app.js` is public. Only the Edge Function has a server-role key. Direct writes to managed route objects and the legacy originals are blocked by restrictive database policies; the old client-side file-delete action has been removed.
- Profile saves create complete versioned Excel objects on the server. Atomic version checks reject concurrent stale writes; they never use last-writer-wins replacement.
- Nearby-stop lookup scans all visible markers per tap; re-evaluate if routes reach many thousands of stops.
- `HEADER_TOOL_LINKS` still has placeholder `#` links.

## Usage assumptions
- Each team/person signs into its own profile. Saves affect only its copy. Sync is manual, authenticated, reviewed, and audited. Reopen a copy to see its most recent saved state; use Review & sync with no pending changes to pull the latest original into it. See [deployment, conflict handling, and recovery](supabase/SETUP.md).
- Phone taps: with Select Stops off a tap opens the customer popup; with it on a tap selects (see `handleMobileStopTap`). Street labels (`updateStreetLabels`) show from zoom 16 when the checkbox is on and Select Stops is off.

- Backup download (top-left ⬇ button): saves the whole open workbook, including current `del_status`, as `<Base>_Backup_YYYY-MM-DD_HHMM.xlsx`. `getDownloadBaseName` strips earlier `_Backup_`/`_Downloaded_` stamps and ` (1)` suffixes so names never grow after download -> upload cycles; the timestamp shows which copy is newest. Keep this behaviour.

- **Cart Delivery tab is shared across phones**: `listFiles` loads `_cart-delivery-tab.json` from the bucket each time; add/remove calls `saveCartDeliveryFileNames()` (async, throws) and reverts on failure. The file is hidden from lists. First load seeds it from the phone's old localStorage list. Don't rename or delete it.

- **Dynamic Island / notch**: `index.html` uses `viewport-fit=cover`; header, sidebar, map and dock offsets use `env(safe-area-inset-*)` (the JS in `placeDeliveryControls`/layout observer measures the real header height, so the sidebar and map start below it). To test, replace `env(safe-area-inset-top)` with `59px` and `env(safe-area-inset-bottom)` with `34px` in a copy of the CSS (iPhone 16 Pro Max values). Any new fixed/absolute element near a screen edge must include the matching `env()` inset.

## Install as a home-screen app (PWA)

On iPhone: open the site in Safari, tap Share, then **Add to Home Screen**. It opens full-screen with its own icon.

- Files: `manifest.webmanifest`, `sw.js`, `icon-192.png`, `icon-512.png`, `apple-touch-icon.png`. The service worker is registered at the end of `app.js`.
- App files use network-first (updates arrive immediately, cached copy only when offline). Map tiles from OpenStreetMap, Esri, Clarity, Austin aerials, and Census city limits share a bounded cache (up to 600) for faster/offline panning. City address queries bypass service-worker caches; their small viewport cache exists only in memory.
- Supabase requests are **never** cached, so delivery data is always live. Profile saves and sync still require a connection; there is no offline queue.
- If you change `sw.js` caching rules, bump the cache names in it.
